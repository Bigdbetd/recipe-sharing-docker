CI/CD Pipeline Reflection

Automated testing improves reliability because the same checks run whenever code is pushed. Manual testing depends on someone remembering every step and checking the same features consistently. My pipeline installs dependencies from lockfiles, runs backend and frontend tests, builds the frontend, and validates both Docker images before deployment can begin. This catches problems in API behavior, React interactions, dependencies, and image construction. Automated tests cannot detect every possible issue, but they provide repeatable checks and clear logs for investigating failures.

For the failure demonstration, I changed a backend test to expect HTTP 200 when creating a recipe, even though the correct response is HTTP 201. GitHub Actions failed the backend test and skipped the remaining validation steps and deployment job. This showed that a failing check prevents a new application version from reaching production. The existing Cloud Run application continued responding while the pipeline was blocked. Restoring the correct expectation fixed the intentional mistake. Deployment setup also showed that authentication and authorization are separate. I used Workload Identity Federation instead of a downloaded service account key, then corrected storage, image-push, logging, and service-account permissions. After these changes, the pipeline deployed both services and checked their public endpoints.

GitHub Actions is convenient for this project because the repository, workflow file, logs, and execution history are available together. GitHub-hosted runners also reduce machine maintenance. Limitations include usage limits, runner availability, and the need to configure deployment credentials carefully. Jenkins offers flexible pipelines and agents that a team can run on its own infrastructure. However, that control also means maintaining the controller, agents, updates, plugins, and security. I would choose GitHub Actions for a small application already hosted on GitHub and consider Jenkins when a company needs extensive infrastructure control or has an established Jenkins installation.

For larger teams, running tests on pull requests gives contributors consistent feedback before merging. Required checks, code reviews, reusable workflows, and parallel jobs could improve coordination. Serializing deployments helps avoid overlapping releases. As the application grows, the team should add broader integration tests, staging checks, and a managed database. Automation makes frequent releases more manageable, but reliable credentials, useful tests, and production monitoring remain necessary.
